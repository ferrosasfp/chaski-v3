### [2026-07-22 01:26] Wave 2 — Export de helper desde un `route.ts` de Next.js rompe `tsc`
- **Error**: exporté `addressEquals` desde `app/api/settle/principal/route.ts` para poder unit-testearlo (T6). `npx tsc --noEmit` falló: `Property 'addressEquals' is incompatible with index signature. Type '(a,b,vm)=>boolean' is not assignable to type 'never'`.
- **Causa raíz**: Next.js App Router genera `.next/types/**/route.ts` que valida los exports de cada `route.ts` contra el set cerrado de handlers HTTP (GET/POST/…). Cualquier export extra debe ser `never` → un helper exportado rompe el typecheck. El gate es `tsc --noEmit` COMPLETO (CD-12), que incluye `.next/types`, así que no se puede exportar aunque en un checkout fresco sin `.next/` pasaría.
- **Fix**: `addressEquals` queda como función **NO exportada** (privada del route). T6 no puede importarla; se cubre la rama EVM vía los 8 tests B1-B6 existentes (byte-idéntico) + la igualdad canónica base58 vía `address.test.ts` (`canonicalizeAddress`) + un test de route en `vm=solana` que prueba el fail-closed PRE-broadcast (CD-5, sin fetch). La rama Solana de `addressEquals` es forward-looking (el settle Solana completo — resolvers/att Solana-aware — es HU-SOL-13), no alcanzable e2e vía la route en esta HU.
- **Aplicar en**: cualquier HU que quiera compartir/testear un helper de un `route.ts` de Next → el helper va en un módulo NO-route (ej. `src/infrastructure/*`), nunca exportado desde el `route.ts`.

### [2026-07-22 15:15] Wave W4 (facilitator) — la 3ª rama del `z.union` widenó `VerifyRequest` y rompió consumers fuera de scope
- **Error**: agregar `SolanaRequestSchema` (sin `extra`, sin `authorization`) al `z.union([Eip3009, NonEip3009, Solana])` de `src/core/schemas.ts` amplió el tipo inferido `VerifyRequest = z.infer<typeof VerifyRequestSchema>` a 3 ramas. `npx tsc --noEmit` COMPLETO falló con 5 errores en archivos PROHIBIDOS por CD-4' (`core/settle.ts:123` y `core/verify.ts:99` leen `parsed.accepted.extra.assetTransferMethod`; `routes/settle.ts:122` y `routes/verify.ts:113` hacen `const parsed: SettleRequest = parseResult.data`). El Story/SDD trató el cambio como "aditivo puro" y solo razonó sobre el `.success` en runtime — NO anticipó el widening del tipo estático hacia los consumers.
- **Causa raíz**: `z.union` prueba ramas en runtime (una request Solana PASA), pero `z.infer` refleja TODAS las ramas en el tipo. Los consumers EVM leen `.extra`/`.authorization` sin narrowing (el check `namespace==='solana'` sobre un string derivado no narrowea la unión en TS). Widenear el tipo rompe esos reads; narrowear el tipo (solo EVM) rompe el `const parsed: SettleRequest = parseResult.data` de las rutas porque `safeParse().data` deriva del schema (3 ramas). Uno u otro consumer rompe — ambos fuera de scope.
- **Fix (100% dentro de `core/schemas.ts`, sin tocar las 2 ramas EVM ni `AcceptedSchema`/`PayloadSchema` ni la línea alias `SettleRequestSchema`)**: se DESACOPLA el runtime del tipo estático. (1) `export type VerifyRequest` se define explícito como la unión de SOLO las 2 ramas EVM (`z.infer<typeof Eip3009RequestSchema> | z.infer<typeof NonEip3009RequestSchema>`) — byte-idéntico al tipo pre-HU. (2) El `VerifyRequestSchema` (unión de 3 ramas, valida Solana en runtime) se asevera como `z.ZodType<VerifyRequest, z.ZodTypeDef, unknown>` vía el cast de frontera sancionado `as unknown as` (mismo patrón `as unknown as SettleParams` de `core/settle.ts:144`). Así `safeParse().data` es el tipo EVM (rutas compilan) y `.extra`/`.authorization` siguen legibles (core compila), mientras el runtime acepta las 3 ramas. Los campos Solana los consume `solana-adapter.ts::_parseSolanaInput` por su propio `params.payload as unknown as {...}` — nunca se leen como `VerifyRequest`. Verificado: EVM byte-idéntico (979/979 verdes, mismas assertions).
- **Aplicar en**: cualquier HU que agregue una rama NO-EVM (Solana/otra VM) a un `z.union` cuyo `z.infer` alimenta consumers que leen campos EVM-only sin narrowing → NO widenear el tipo exportado; mantenerlo EVM y asertar el output del schema con `as unknown as z.ZodType<TipoNarrow>`. Es el patrón para "runtime valida N ramas, tipo estático expone M<N" sin tocar los consumers.
